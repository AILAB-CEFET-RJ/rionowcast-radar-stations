# Dataset V4: Radar Sumare 2025--2026

## Escopo

Esta versao estende o dataset auditavel V3 sem modifica-lo. A raiz prevista e
`data/datasets/radar_sumare_2012_2026_15min_128_audited_v4`. Os PNGs novos
sao entregues como arquivos mensais em
`/home/ebezerra/dados/sumare/2025-2026/`.

O AlertaRio disponivel cobre 2025 integralmente e 2026 de 1 de janeiro ate 26
de junho, 05:15 UTC. O radar pode ser gerado para toda a cobertura entregue de
2026, mas somente a intersecao com os targets AlertaRio sera elegivel para
treino ou avaliacao supervisionada.

## 1. Inventariar e Extrair a Fonte

Use uma raiz bruta nova. Nao extraia arquivos novos em `data/radar_sumare/` e
nao altere o dataset V3.

```bash
cd ~/ailab/rionowcast-radar-stations
conda activate ailab

archives=/home/ebezerra/dados/sumare/2025-2026
raw=data/raw/radar_sumare_2025_2026_v4
report=outputs/analysis/radar_sumare/v4

PYTHONPATH=src python -u -m nowcasting.cli.stage_radar_sumare_archives \
  --archive-root "$archives" \
  --raw-root "$raw" \
  --output-manifest "$report/source_archives_manifest.json" \
  --year-start 2025 --year-end 2026 \
  --extract
```

O comando calcula SHA-256 de cada arquivo, exige o layout
`AAAA/MM/DD/AAAA_MM_DD_HH_MM.png`, recusa links e caminhos inseguros, e cria
um manifesto versionado. O timestamp canônico é o nome do PNG: divergências
entre o dia no diretório, o mês do arquivo e a data no nome são registradas no
manifesto, pois a fonte pode particionar capturas próximas à meia-noite pelo
momento de recebimento. Essas divergências não interrompem o staging; a
auditoria temporal dos PNGs determina a cobertura efetiva. Uma retomada depois
de interrupcao exige `--resume`; ela somente aceita PNGs ja presentes com o
mesmo tamanho do membro original.

## 2. Auditar PNGs

Os PNGs V4 sao RGBA de `1024 x 768`, diferentemente do bitmap historico de
`656 x 654`. A inspecao inicial confirmou essa geometria em todos os 378.154
arquivos e o layout e compativel visualmente com o crop operacional
`(left=185, top=56, right=839, bottom=712)`, que resulta em `654 x 656`.
O contrato separado abaixo foi validado com o AlertaRio e pode ser usado para
gerar os memmaps V4.

```bash
config=configs/radar_sumare_2025_2026_capture_candidate_v1.json

PYTHONPATH=src python -u -m nowcasting.cli.audit_radar_pngs \
  --data-root "$raw" \
  --output-dir "$report/png_audit" \
  --year-start 2025 --year-end 2026 \
  --capture-config "$config" \
  --verify-images
```

### Validacao espacial e temporal

O recorte acima foi validado contra 100 eventos AlertaRio de 2025 e outros
100 de 2026. A orientacao `direct` do mapeamento historico foi a lider nos
dois anos: correlacao de postos entre sinal local do radar e `m15` de 0,597 em
2025 e 0,682 em 2026. Em 2025, o offset de `-15` minutos foi superior em
correlacao de postos aos controles `-30` (0,471) e `0` (0,541). Assim, o
contrato V4 usa nomes de PNG em `America/Sao_Paulo`, janelas de radar indexadas
pelo inicio UTC e `m15` indexado pelo fim da janela, com deslocamento `-15`.

Os artefatos auditaveis estao em
`outputs/analysis/radar_sumare/v4/mapping_audit_2025_offset_minus15/`,
`mapping_audit_2025_offset_minus30/`, `mapping_audit_2025_offset_0/` e
`mapping_audit_2026_offset_minus15/`.

Antes de gerar memmaps, revisar dimensoes, PNGs invalidos, cobertura de janelas
de 15 minutos, lacunas e previews. A validacao contra eventos AlertaRio ja
confirmou que o mapeamento espacial e a convencao temporal permanecem
adequados para o produto de radar recente.

## Estado da Materializacao

A raiz V4 foi materializada e auditada sem modificar o dataset V3. Os anos
2012--2024 preservam os artefatos anteriores, enquanto 2025--2026 usam o novo
contrato de captura, metadados de cobertura e regra de QC. O dataset V3

## 3. Materializar a Raiz V4

Os anos 2012--2024 devem ser reutilizados por hardlinks, mantendo seus bytes e
metadados V3 imutaveis. Somente 2025--2026 sao construidos a partir dos PNGs
novos. O comando abaixo exige que origem e destino estejam no mesmo filesystem;
ele falha antes de copiar dados se a raiz V4 ja existir.

```bash
v3=data/datasets/radar_sumare_2012_2024_15min_128_audited_v3
v4=data/datasets/radar_sumare_2012_2026_15min_128_audited_v4

test ! -e "$v4" || { echo "Destino V4 ja existe: $v4"; exit 1; }
mkdir -p "$v4"
cp -al "$v3"/year=* "$v4"/

PYTHONPATH=src python -u -m nowcasting.cli.build_radar_memmaps \
  --data-root "$raw" \
  --output-root "$v4" \
  --year-start 2025 --year-end 2026 \
  --capture-config "$config" \
  --dataset-contract radar_sumare_audited_v4
```

Depois, gere os targets AlertaRio somente para 2025 e para a parte observada de
2026. A disponibilidade efetiva sera dada pelos timestamps do radar e pelas
observacoes validas, e nao pelo fim nominal do ano.

```bash
PYTHONPATH=src python -u -m nowcasting.cli.build_alertario_sparse_targets \
  --alertario-root data/pluviometricos_alertario \
  --mapping configs/mapeamento_pixel_estacao_alertario_historical_v1.csv \
  --radar-root "$v4" \
  --output-root "$v4" \
  --year-start 2025 --year-end 2026 \
  --height 128 --width 128 \
  --height-orig 656 --width-orig 654 \
  --observation-to-radar-offset-minutes -15 \
  --max-m15-mm 100
```

O limite superior e uma regra de QC versionada, nao um truncamento do target.
Se uma leitura exceder `100 mm/15 min`, a observacao daquela estacao na janela
e mascarada como ausente. A auditoria encontrou dez targets acima desse limite
em 2026, com maximo de `417,2 mm/15 min`. Eles eram saltos isolados nas estacoes
Barra/Barrinha e Piedade. A auditoria espacial posterior encontrou suporte de
ocorrencia para parte desses casos, mas nao confirmou quantitativamente suas
magnitudes extremas. De 2012 a 2025, o maior target observado foi
`72,0 mm/15 min`. O metadata registra o limite, a acao de exclusao e as
contagens afetadas.

## 4. Elegibilidade Supervisionada e Protocolo Cronologico

Os metadados de target de 2025--2026 ativam a politica
`sample_eligibility.require_observation_in_each_output_frame`. Para uma amostra
com cinco horizontes futuros, cada horizonte deve conter ao menos uma
observacao AlertaRio valida. A regra evita que trechos cobertos apenas pelo
radar produzam loss mascarada igual a zero e sejam contabilizados como
amostras supervisionadas. Metadados antigos sem essa politica preservam o
comportamento da V3.

A cobertura observada apos o QC e:

| Ano | Frames de radar | Frames com target | Sequencias elegiveis |
|---|---:|---:|---:|
| 2025 | 25.291 | 25.291 | 4.540 |
| 2026 parcial | 24.892 | 15.446 | 2.847 |
| Teste conjunto | 50.183 | 40.737 | 7.387 |

Em 2026, o ultimo target `m15` termina as 05:15 UTC de 26 de junho e se
alinha ao frame de radar iniciado as 05:00 UTC. Os 9.446 frames de radar
posteriores permanecem no acervo V4, mas nao entram em treino ou avaliacao
supervisionada.

O protocolo principal da V4 usa treino em 2012--2022, validacao em 2023--2024
e teste continuo de 1 de janeiro de 2025 a 26 de junho de 2026. O teste
conjunto contem duas estacoes chuvosas e e o resultado principal. Para tornar
a composicao sazonal transparente, os resultados devem tambem ser reportados
separadamente para 2025 completo e 2026 parcial, sem usar qualquer parte do
teste para selecionar hiperparametros, checkpoints ou limiares de alerta.

## 5. Auditoria Temporal Diagnostica do AlertaRio

O limite absoluto de `100 mm/15 min` nao detecta sozinho resets, propagacao de
telemetria incorreta ou picos suspeitos abaixo desse limite. A auditoria abaixo
avalia a consistencia temporal dos acumulados originais, sem alterar targets e
sem excluir observacoes:

```bash
PYTHONPATH=src python -u -m nowcasting.cli.audit_alertario_temporal_consistency \
  --input-root data/pluviometricos_alertario \
  --output-dir outputs/analysis/alertario/temporal_consistency_2026_v1 \
  --year-start 2026 --year-end 2026
```

O diagnostico testa, em cadencia continua de cinco minutos, as hipoteses
`m10(t) = m05(t) + m05(t-5)`, `m15(t) = m05(t) + m05(t-5) + m05(t-10)` e
`h01(t)` como soma dos doze `m05` mais recentes. Tambem identifica picos altos
isolados e violacoes da hierarquia `m05 <= m10 <= m15 <= h01`. Os artefatos
`flagged_observations.parquet`, `flagged_examples.csv`,
`flagged_episodes.csv`, `station_year_summary.csv` e `summary.json` sao
exclusivamente diagnosticos. Linhas consecutivas sinalizadas na mesma estacao
sao agrupadas em `flagged_episodes.csv`, para que a propagacao de uma unica
ocorrencia pelos acumulados nao seja contada como varios eventos independentes.
Uma regra adicional de exclusao somente deve ser definida depois de validar a
semantica dos acumulados e os casos sinalizados com o AlertaRio.

### Resultado da auditoria de 2026

A execucao `temporal_consistency_2026_v1` auditou 1.672.694 pares
estacao--timestamp das 33 estacoes e sinalizou 93 timestamps, agrupados em 18
sequencias diagnosticas contiguas. Nao foram encontrados timestamps duplicados
nem violacoes da hierarquia dos acumulados. Entre as janelas comparaveis,
foram encontradas 5 inconsistencias em `m10`, 10 em `m15` e 72 em `h01`, sobre
1.669.743, 1.668.510 e 1.659.163 comparacoes, respectivamente.

Os maiores erros de consistencia concentram-se em Barra/Barrinha (417,2 mm) e
Piedade (260,2 mm), incluindo picos isolados seguidos por acumulados que voltam
a valores proximos de zero. Ha tambem diferencas muito menores, de 0,2 mm, em
outras estacoes. Alem disso, alguns valores altos propagam-se de maneira
aritmeticamente consistente entre `m05`, `m10`, `m15` e `h01`. Portanto, os 93
timestamps nao constituem uma lista de rejeicao: eles delimitam casos para
inspecao e confirmacao semantica com o AlertaRio. Nenhum target da V4 foi
alterado nesta etapa.

## 6. Auditoria Espacial Diagnostica do AlertaRio

Os 93 timestamps sinalizados temporalmente foram enriquecidos com tres fontes
de contexto, sem modificar os targets:

1. observacoes AlertaRio de estacoes vizinhas em raios de 5 e 10 km, com
   tolerancia temporal de 15 minutos;
2. presenca de sinal RGB do radar em patches de 3 por 3 e 5 por 5 pixels;
3. consenso positivo opcional de estacoes WebSirene previamente aprovadas pelo
   QC e com observacoes classificadas como `accepted`.

O radar e usado apenas para identificar eco visual; o RGB nao e refletividade
quantitativa e nao confirma a magnitude da chuva. Da mesma forma, uma estacao
vizinha molhada confirma somente a ocorrencia local de chuva, nao que um valor
extremo na estacao candidata esteja correto. O WebSirene e deliberadamente
assimetrico: consenso positivo pode acrescentar suporte, mas ausencia de chuva,
ausencia de dados ou discordancia nunca constituem evidencia negativa, e essa
rede nao pode determinar rejeicao sozinha.

Os parametros ficam versionados em
`configs/alertario_spatial_qc_v1.json`. Para reproduzir a auditoria:

```bash
PYTHONPATH=src python -u -m nowcasting.cli.audit_alertario_spatial_consistency \
  --candidate-observations \
    outputs/analysis/alertario/temporal_consistency_2026_v1/flagged_observations.parquet \
  --alertario-root data/pluviometricos_alertario \
  --alertario-mapping data/mapeamento_pixel_estacao_alertario.csv \
  --dataset-root data/datasets/radar_sumare_2012_2026_15min_128_audited_v4 \
  --config configs/alertario_spatial_qc_v1.json \
  --output-dir outputs/analysis/alertario/spatial_consistency_2026_v1 \
  --websirene-root data/processed/websirene_qc/v1 \
  --websirene-mapping data/mapeamento_pixel_estacao.csv \
  --websirene-whitelist outputs/analysis/websirene/qc/v1/station_whitelist.csv
```

O diagnostico preserva os 93 timestamps e as 18 sequencias temporais da etapa
anterior. Para triagem humana, tambem agrupa candidatos da mesma estacao
separados por no maximo 60 minutos em um `episodio de revisao`; isso nao define
um evento meteorologico. Um episodio recebe prioridade alta quando combina ao
menos uma inconsistencia temporal e ao menos um pico sem suporte das fontes
disponiveis, ainda que essas evidencias estejam em timestamps distintos.

### Resultado da auditoria espacial de 2026

Dos 93 candidatos, 22 tinham `m15 >= 6,25 mm/15 min` e foram submetidos a
triagem espacial. A classificacao por timestamp foi:

| Diagnostico | Timestamps |
|---|---:|
| Abaixo do limiar de triagem espacial | 71 |
| Sem suporte das fontes disponiveis | 15 |
| Isolado nos pluviometros, com eco RGB | 3 |
| Contexto espacial insuficiente | 3 |
| Ocorrencia apoiada apenas no raio ampliado | 1 |

Os candidatos formaram 12 episodios de revisao, dos quais 5 receberam
prioridade alta. Havia frame de radar alinhado para 65 dos 93 timestamps. O
WebSirene estava configurado com 80 estacoes aprovadas, mas nao possui arquivos
de 2026; por isso, forneceu zero observacoes e nao foi interpretado como
discordancia.

O caso de Piedade ilustra a separacao entre ocorrencia e magnitude: o pico de
`260,4 mm/15 min` coincidiu com eco RGB e com uma estacao ampliada molhada, mas
o maximo dessa vizinha foi apenas `2,6 mm/15 min`. O artefato registra ambos os
valores para revisao; ele nao declara que a magnitude de Piedade foi validada.

Os resultados detalhados sao `spatial_observations.parquet`,
`review_candidates.csv`, `spatial_episode_summary.csv`,
`station_neighbor_graph.csv` e `summary.json`. A execucao produziu zero
exclusoes automaticas. Qualquer nova regra de mascara exige inspecao dos casos,
confirmacao semantica com o AlertaRio e uma configuracao de QC nova.

### Material para revisao meteorologica

O exportador abaixo transforma os artefatos tecnicos em uma planilha Excel com
horario local e UTC, casos prioritarios, todos os episodios, observacoes
detalhadas, legenda e campos para o parecer da meteorologista. Ele tambem gera
um documento curto com as perguntas a serem encaminhadas:

```bash
review=outputs/analysis/alertario/revisao_meteorologica_2026

PYTHONPATH=src python -u -m \
  nowcasting.cli.export_alertario_meteorologist_review \
  --episodes \
    outputs/analysis/alertario/spatial_consistency_2026_v1/spatial_episode_summary.csv \
  --observations \
    outputs/analysis/alertario/spatial_consistency_2026_v1/spatial_observations.parquet \
  --output-workbook "$review/revisao_alertario_2026_juliana.xlsx" \
  --output-questions "$review/perguntas_para_juliana.md"
```

A prioridade da planilha ordena a revisao humana; nao e uma decisao de
exclusao. Ela inclui os cinco episodios que combinam inconsistencia temporal e
ausencia de suporte, alem dos episodios com `m15 >= 100 mm/15 min`, mesmo
quando havia eco RGB ou chuva fraca em uma estacao vizinha.
